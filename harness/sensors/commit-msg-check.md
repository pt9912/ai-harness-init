# `make commit-msg-check` — prüft eine Commit-Message-Datei gegen Traceability-Kennung

## Vertrag

`make commit-msg-check MSG=<datei>` prüft eine Commit-Message-**Datei** (nicht die Historie) gegen das `commits:`-Modul aus [`.d-check.yml`](../../.d-check.yml) via `--commit-msg` — wie `slice-mv`/`archive-welle`/`vendor-baseline` **kein Gate und in keiner Prerequisite-Kette**: `MSG` variiert pro Aufruf und ist damit kein hermetischer Prüfbereich ([`LH-QA-01`](../../spec/lastenheft.md#lh-qa-01--keine-halluzinierten-gates-f4-f5-f6)). Geprüft wird **nur die Anwesenheit** einer Kennung aus `commits.id-patterns` (`ADR-\d{4}`, `LH-[A-Z]{2}-\d{2}`, `MR-\d{3}`, `slice-\d+`) — **nicht ihre Wahrheit**: eine Message, die zusätzlich einen nicht auflösbaren Hash nennt, geht mit derselben Kennung ebenso durch (derselbe Befund wie bei `doc-commits`, gemessen mit `--commit-msg` gegen eine Datei mit `0f8d1a1` **und** `slice-1`: Exit 0). Rot gesehen an einer echten Message-Datei ohne jede Kennung (`d-check: commit-untraceable — Commit-Message ohne DC-/ADR-/MR-/slice-ID: "…"`, Exit 1); grün an derselben Datei mit `slice-1` ergänzt (Exit 0) — beide Läufe stehen im Umsetzungs-Commit.

Der **Träger** ist ausschließlich der PreToolUse-Zusatz-Hook [`.claude/hooks/pretooluse-commit-msg-guard.sh`](../../.claude/hooks/pretooluse-commit-msg-guard.sh), zweiter Eintrag im `"Bash"`-Matcher neben `pretooluse-command-guard.sh` ([`.claude/settings.json`](../../.claude/settings.json)): er erkennt einen `git commit`-Aufruf, der eine Message-Datei per `-F`, `--file` oder `--file=` übergibt — unquotiert, in einfachen oder doppelten Anführungszeichen (der Inhalt darf Leerraum enthalten), sowie mit `-F` als letztem Zeichen eines kombinierten Kurz-Flags (etwa `-qF`) —, und spiegelt sie (Repo-Konvention „Commit via Message-Datei") **vor** der Ausführung nach `make commit-msg-check MSG=<datei>`; er blockt bei Exit ≠ 0 — der Commit steht dann nicht. Bewusst ausgenommen bleibt `-F -` (stdin, keine zu prüfende Datei). `git commit -m "…"` entkommt in der Praxis ebenso, aber **nicht garantiert**: Der Matcher liest die Befehlszeile flach, ohne Quotierungs-Kontext — trägt der `-m`-Text selbst eine `-F`/`--file`/`--file=`-Form gefolgt von einem existierenden Pfad, greift der Hook trotzdem und prüft diesen Pfad wie eine Message-Datei (derselbe Stolperdraht-Charakter wie beim Nachbar-Guard, kein Sandbox-Anspruch, [ADR-0004](../../docs/plan/adr/0004-durchsetzungs-emission.md)). Im gelebten Bestand ohne Treffer: `git log --format='%s' | grep -cE '[[:space:]](-[a-zA-Z]*F|--file)(=|[[:space:]])'` → 0 von `git log --format='%s' | wc -l` Betreffs, beide kein Erwartungswert — erreichbar, nicht eingetreten. Ein in Anführungszeichen gesetzter Pfad, der eine Shell-Variable enthält, bleibt unexpandiert — wie im unquotierten Fall auch; die Existenzprüfung greift für diesen Pfad **dauerhaft** nicht, nicht nur vorübergehend (kein Rateversuch, keine Shell-Expansion). Fehlt die Message-Datei aus einem anderen Grund — etwa weil sie erst nach dem Hook-Lauf entsteht —, greift der Hook ebenfalls nicht. **Ein zweiter, strukturell verschiedener blinder Fleck:** Der Hook sieht nur, was als Bash-Tool-Kommando **wörtlich** `git commit …` enthält — ein Commit, der **innerhalb** eines anderen Skripts oder Binaries läuft (etwa `harness/tools/slice-mv.sh`, aufgerufen über `make slice-mv`), erscheint dem Hook als `make slice-mv …` und wird nie geprüft, unabhängig von Flag-Form oder Kennung. Gemessen am Bestand: `git log --format='%s' | grep -c '^slice-mv:'` → 304 von `git log --format='%s' | wc -l` Betreffs (rund 14 %, kein Erwartungswert) entstehen auf diesem Weg; `archive-welle`/`vendor-baseline` committen ebenso aus dem Go-Binär heraus und sind aus demselben Grund unerreichbar, tragen im heutigen Bestand aber noch keinen Commit (`git log --format='%s' | grep -c '^archive-welle'` → 0). Ein Vor-Commit-Hook auf Bash-Tool-Ebene deckt damit **nur** direkt getippte `git commit`-Aufrufe — ob dieser Rest über einen `git`-eigenen `commit-msg`-Hook geschlossen wird (ein anderer Träger, mit eigener Bootstrap-Entscheidung), ist hier **nicht** entschieden. Die Prüf-Instanz ist über `PRETOOLUSE_COMMIT_MSG_CHECKER` austauschbar (Default: der `make`-Aufruf oben); einziger Grund ist Testbarkeit — das gepinnte `BATS_IMAGE` fährt ohne Docker und ohne `git` (dieselbe Grenze wie bei `slice-mv`/`archive-welle`), `test/commit-msg-guard.bats` hält Match-Extraktion, Datei-Existenz-Vorprüfung und beide Verdikte der (gestubbten) Prüf-Instanz hermetisch — jede erkannte Aufrufform (unquotiert, beide Quotierungs-Formen, `--file`, `--file=`, kombiniertes Kurz-Flag) mit einem eigenen Fall; der reale `docker`/`make`-Lauf gegen eine echte Datei steht oben in diesem Absatz, nicht im bats-Fall. `test/mutations/307-commit-msg-guard-block-bedingung-invertiert.sh` nimmt der Block-Bedingung die Zähne (Kennungs-Prüfung wirkungslos) und muss `test/commit-msg-guard.bats` röten.

**Der Prüfbereich trägt seinen Cutoff, und er ist rein prospektiv.** Ein Maßstab über die ganze Historie wäre an einem Bestand rot, den niemand mehr ändern kann ([`LH-QA-01`](../../spec/lastenheft.md#lh-qa-01--keine-halluzinierten-gates-f4-f5-f6), dieselbe Cutoff-Begründung wie [`MR-015`](../conventions.md#mr-015--change-request-bei-personalunion-von-auftraggeber-und-entwickler)): gemessen (`RE='ADR-[0-9]{4}|LH-[A-Z]{2}-[0-9]{2}|MR-[0-9]{3}|slice-[0-9]+|^(Merge |Revert )'`)
`git log --format='%s' | grep -vcE "$RE"` → **239** Commit-Betreffs der gesamten Historie ohne Kennung,
`git log --format='%s' | wc -l` → **2105** Betreffs insgesamt,
`git log --format='%s' -50 | grep -vcE "$RE"` → **3** in den letzten 50,
`git log --format='%s' -20 | grep -vcE "$RE"` → **0** in den letzten 20 —
alle vier **kein Erwartungswert**, sie wandern mit jedem Commit; ein rückwirkender Sensor wäre am Tag seiner Aktivierung tief rot. Der PreToolUse-Hook prüft strukturell nur den **werdenden** Commit, nie die Historie — er braucht deshalb keinen Cutoff-Zeitpunkt: Der Cutoff **ist** „ab dem ersten Aufruf dieses Hooks", nicht ein Datum in der Konfiguration. `doc-commits` (`d-check.mk`, `--range`) bleibt darum advisory und ungenutzt für diese Zusage — nicht aus Vorsicht, sondern gemessen defekt: Der gepinnte `v0.74.1` bricht `--range`-Läufe des `commits`-Moduls mit `Range-Basis-Vorfahren nicht lesbar: object not found` ab, sobald `commits.id-patterns` **irgendeine nicht-leere** Liste trägt — auch die drei eingebauten Muster `ADR-\d{4}`/`DC-(FA-[A-Z]+|QA)-\d+`/`slice-\d+` **verbatim** brechen ab (gemessen an einer Kopie außerhalb des Repos, netzlos, Digest aus `d-check.mk`); nicht die *Abweichung* von den Vorschlägen ist die unterscheidende Variable, sondern die bloße *Anwesenheit* einer expliziten Liste — reproduziert unabhängig von Range-Tiefe (`HEAD~1..HEAD` bricht ebenso wie `HEAD~20..HEAD`), von expliziten Commit-Hashes statt `HEAD~N`, und von den `--disable`-Flags; verschwindet mit einer **leeren** (`id-patterns: []`) oder **ganz weggelassenen** `id-patterns`-Liste — dann bricht `--range` zwar nicht mehr ab, prüft aber auch nichts mehr: **0 Befund(e), Exit 0**, gemessen an einer Kopie außerhalb des Repos, deren jüngste Commit-Betreffs keines der drei Muster tragen; `--print-config` führt zu `commits.id-patterns` keinen aktiven Default, der ganze `commits:`-Block steht dort als auskommentierter Vorschlag — es laufen also **keine** eingebauten Muster, sondern gar keine Prüfung. Dasselbe stille Grün wie bei einer leeren, aber auflösbaren Range im Sensor [`history-range-guard`](history-range-guard.md) ([`MR-007`](../conventions.md#mr-007--baseline-committet-vendored-statt-gefetchter-cache) Setzung 3). Fehlerfrei **und** weiter prüfend bleibt nur `--commit-msg` mit der **realen**, nicht-leeren `id-patterns`-Liste (s. o., `commit-msg-check`) — dieselbe leere Liste bricht dort stattdessen laut ab (`--commit-msg braucht konfigurierte commits.id-patterns`, Exit 2). `--enable vcs`/`doc-immutable` mit demselben `commits:`-Block im Baum bleibt unberührt (isoliert an derselben Kopie). Ein Range-Lauf in CI ist damit **nicht** in diesem Slice entschieden — er bräuchte entweder einen Tool-Fix oder den vollständigen Verzicht auf eine explizite `id-patterns`-Liste an dieser Stelle (nicht bloß auf `LH-*`/`MR-*` darin — das allein trägt nicht, s. o.), beides eine eigene Abwägung. `d-check` ist ein Nachbar-Repo desselben Nutzers; eine hier gemessene Modul-Lücke ist dort eine **Anforderung**, keine feste Werkzeug-Grenze.
